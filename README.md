# Utsushi

動画・音声をローカルだけで文字起こしする macOS アプリ。Python もサーバも使わない単体の `.app`。

## 何をするか

1. 動画から音声を取り出す（AVFoundation。ffmpeg を同梱しない）
2. 文字起こしする（whisper.cpp / Metal、または OS 内蔵の SpeechTranscriber）
3. **ハルシネーションを機械的に潰す**（後述）
4. 系統の違う別エンジンで読み直し、食い違う箇所を洗い出す（sherpa-onnx）
5. 食い違いを LLM に判定させる（候補の**番号**しか返せない形にしてある）
6. 日本語として校正する（Apple Foundation Models、ただし提案は全てゲートを通す）
7. 要点を抜き出す（本文は引用そのまま。要約文をモデルに書かせない）
8. Markdown / SRT / VTT / TXT / JSON に書き出す

一貫している原則はひとつだけ:
**モデルには「選ばせる」か「案を出させる」しかさせず、本文はコードが組み立てる。**

## ハルシネーション対策

whisper 系は無音や雑音に対して必ず何かを喋る。これは確率的な事故ではなく構造的な性質なので、
プロンプトや閾値ではなく決定論的な手段で潰している。

| 層 | 手段 | 効果 |
|---|---|---|
| 無音ゲート | 区間のピーク音圧が閾値未満なら本文を無条件破棄 | 「ご視聴ありがとうございました」系の幻聴が原理的に出力に残らない |
| 反復ループ検出 | 同一本文が3回以上連続したら全て破棄 | 30秒刻みのループ出力を除去 |
| 既知フレーズ | 低音圧区間に限って既知の幻聴フレーズを破棄 | 本当にそう言っている場合は残す |
| 密度異常検出 | 尺に対して文字数が少なく、かつ有声区間が5秒以上ある区間を検出 | VADが発話を無音と融合して潰した箇所を発見 |
| 自動再認識 | 疑わしい区間だけ VAD を切って読み直し、情報量が増える場合のみ差し替え | 取りこぼしを回復。改悪はしない |

## 校正のハルシネーション対策

**LLM には文章を書かせない。書き換え案を出させ、機械的に検証して落とす。**

```
原文 ──▶ 辞書（決定論）──▶ 表記・フィラー規則（決定論）──▶ LLM 提案 ──▶ EditGate ──▶ 採用/棄却
                                                                   ↑
                                                    ここを通らない案は原文のまま残る
```

`EditGate` の通過条件（`Sources/UtsushiCore/Correction/EditGate.swift`）:

- **読み一致**: `CFStringTokenizer` で書き換え前後の読みを取り、一致しない案は棄却。
  音声認識の誤りは同音異義語なので、正しい修正は読みを変えない。
  「機構→気候」は通り、「御社→貴社」「新小物→BeeX」は通らない。
- **英数字トークンの新規出現を禁止**: 原文に無い英単語をモデルが創作するのを止める独立した防壁。
- **長さ比 0.75〜1.35 / 編集距離 40 以内**: 水増しと要約を止める。
- **2回一致**: 同じ提案が2回出た場合のみ採用（既定で有効）。

これらはプロンプトではなくコードで強制されている。緩めるにはソースを変更する必要がある。

読みごと違う誤認識（社名・人名）は設計上 LLM では直らない。直す唯一の経路が**固有名詞辞書**で、
これはモデルに固有名詞を推測させないための意図的な線引き。

原文は `Segment.original` に必ず残り、校正結果は差分として提示され、1件ずつ元に戻せる。

## 別エンジンとの照合

同じ音声を系統の違うエンジンで認識し、出力が食い違う箇所を取り出す
（`Sources/UtsushiCore/CrossCheck/`）。一致していれば信用でき、食い違えば怪しい。

同じ11分の素材（実音声・有声160秒）での実測:

| エンジン | 系統 | 速度 | 文字数 | ライセンス |
|---|---|---|---|---|
| whisper large-v3-turbo | encoder-decoder | 92倍速 | 1,064 | MIT |
| SenseVoice-Small | 非自己回帰 | **90倍速** | 1,104 | Apache-2.0 |
| ReazonSpeech-k2-v2 | zipformer transducer | 60倍速 | 952 | Apache-2.0 |
| parakeet-tdt_ctc-0.6b-ja | NeMo CTC | 29倍速 | 1,006 | CC BY 4.0（帰属表示が要る。出力にも自動で載る）|

whisper large-v3 を足しても意味が薄い。turbo はその蒸留なので誤りが相関し、
アンサンブルとして独立していない。**系統を変えることに意味がある。**

### 試して外したもの

**Qwen3-ASR 0.6B（LLMデコーダ型）** は選べる状態で残してあるが、既定では勧めない。
同じ音声・同じ設定・temperature 0・シード固定でも、プロセスをまたぐと出力が変わる
（753 / 758 / 759 文字）。同一インスタンス内では一致するので、原因は
onnxruntime の並列リダクション順あたりが疑わしいが**特定できていない**。
照合の相手にすると「前回は決着した箇所が今回は未決」が起きて、CER を測っても再現しない。
速度も 6.7 倍速で他の1桁下。設定画面にこの内容が出るようにしてある。

**sherpa-onnx-sense-voice-…-2025-09-09** は使っていない。名前が続いているので
SenseVoice の新版に見えるが、onnx のメタデータは `comment=ASLP-lab/WSYue-ASR` で
**広東語向けの別モデル**だった。日本語を食わせるとかなが落ちて漢字だけになる
（11分で287文字）。使っているのは 2024-07-17 版（本家 FunASR の SenseVoice-Small）。

食い違いの判定は `DisagreementAdjudicator`。`@Generable enum` で
「候補の番号」しか返せない形にしてあるので、モデルが第3の文字列を創作する余地が構造的に無い。
読みが一致する食い違い（機構／気候）と読みが違う食い違いは別々に集計される。
前者は音響で区別できないので文脈判断が正しい道具だが、後者は音響に情報が残っているため、
テキストだけの判断は確度が落ちる。混ぜて「N件判定した」と報告しないのはそのため。

### 食い違いを4つに分けて、人に見せるものを絞る

実データ（11分・4エンジン）で人に残っていた282件を手で読んだところ、
**実際に見る価値があったのは約5%** だった。残りは認識の誤りではないものが占めていた。
そこで機械的に分類し、既定では中身の違いだけを出す。

| | 何か | 実測 |
|---|---|---|
| 中身の違い | 人が見るべきもの | 171 |
| 整列のずれ | 片方の窓に寄っただけ。本文は両方にある | 78 |
| 語尾・助詞のゆれ | 「と」/「って」。収録全体でくり返す | 39 |
| 表記だけの違い | 「三月」/「3月」「いただ」/「頂」 | 26 |

**どれも捨てない。** 分類はすべて機械的な近似で外すことがあるので、件数は常に画面に出し、
チェックひとつで全件たどれる。「見せない」であって「無かったことにする」ではない。

分類で気をつけていること:

- **くり返しだけを根拠に畳まない。** 誤認識された社名・人名はくり返し出るので、
  回数だけを条件にすると一番拾いたいものを一番確実に隠すことになる。
  `.inflection` はひらがなと約物だけでできた組み合わせに限っている
- **片側が空でも、隣接窓に本文が無ければ残す。** それは本当の取りこぼしなので
- **同音異義語（機構／気候）は畳まない。** 両方が漢字なら交ぜ書きではない

#### まだ多すぎる（未解決）

282件 → 171件まで落ちたが、11分で171件は依然として多い。
そして **282 → 190 → 171 と、手を入れるたびに効きが落ちた。**

原因は分類ではなく比較の単位にある。10秒の窓で文字列を機械的に突き合わせているので、
スパンが語の途中で切れる（「コンピ」「ログアウ」「Teamsはログアウ」）。
断片には読みが定義できないので読み一致の判定が使えず、片側が空になるものも増える。
分類はその症状に名前を付けられるだけで、原因は消せない。

直すなら文（。？！と長い間）を単位に整列し直す必要がある。`TranscriptAlignment` の
作り直しになるので手を付けていない。**また、正解データが無い状態で件数だけを
追いかけると「本物を捨てて件数が減った」と区別がつかない。** 先に必要なのはそちら。

### 表記をそろえてから比べる

zipformer は「三月」、parakeet は「3月」と書く。認識は合っているのに食い違いとして並ぶ。

`Notation`（`Sources/UtsushiCore/Text/`）で漢数字・全角・半角をそろえてから比較する。
着手前は「食い違いの大半が表記差だろう」と踏んでいたが、実測では 574 件中 29 件（5%）で
**見立ては外れた**。表記差を分けることに価値はあるが、件数の主因ではなかった。

同じ正規化は要約の見張り（`SummaryGate`）でも使う。以前は要約側にだけ実装があり、
同じ「三月／3月」が要約では同一・照合では食い違い、という状態になっていた。

比較の単位もここで揃えている。以前は時間窓 10 秒に対してセグメントが 20〜27 秒あると、
1つのセグメントが複数の窓に丸ごと入り差分が水増しされていた（574件）。現在は、単語時刻を
持たないエンジンにも共通して適用できるよう、重なった時間比で本文の文字範囲を分割する。
隣接窓の境界には同じ丸めを使い、文字の欠落・重複が起きないことをテストしている。
長さ0のセグメント（`SpeechAnalyzer` は `end == start` を作る）は時間比で分けられないので、
その時刻を含む窓へ丸ごと入れる——捨てると本文が照合から静かに消える。

## 書き出しは LLM に渡される前提で作る

この文字起こしは人が読むだけでなく、そのまま別の LLM に渡されることを想定している。
そのとき効く条件は、人が読むときとは違う。

**人は本文と後ろの検証記録を目で突き合わせられるが、LLM は突き合わせない。**
本文を確定した事実として読み、怪しい語を根拠に自信を持って間違える。
だから「どこが怪しいか」は本文と同じ場所に無いといけない。

```
`[00:00:34]` 当社は結構一気通貫で横のつながりも実際にあったりはするので、…
> ↳ 別エンジンの候補: 「貫」→「関」 / 「一」→「意」
```

**本文は書き換えない。** 候補を添えるだけで、原文には触らない
（読みやすく直した文を渡すと、直した箇所が事実として固定される）。

添える条件を絞ってあるのは、全部出すと本文が読めなくなるため:

- 中身の違いだけ。整列のずれ・語尾のゆれ・表記差は読み手の判断を変えない
- 両側に本文がある。片側が空は代わりの語を示せないので、読み手にできることが無い
- **その語が実際にその行にあること。** 食い違いの時刻は10秒の窓なので、
  重なりだけで拾うと隣の行にも同じ注記が付く（実際に付いていた）
- 長さが釣り合っていること。「〜人事の方」→「まずで実際」のような組を候補として見せると、
  節まるごとが別物かのように読める

これで11分の素材に対し注記15行。実際に拾えているのは「部長陣→部長人」「一気通貫→一気通関」など。

冒頭には「この文書の読み方」を置き、記号の意味と**既知の弱点**を先に宣言する:

- 同音異義語と固有名詞を取り違える。意味が通らない語は誤認識を疑うこと
- **話者の区別をしていない。** 複数人の会話でも1人の連続した発話に見える
- 数値・固有名詞・日付は、この文書だけを根拠に確定しない

検証記録の節にも「ここから下は話された内容ではない」と明記してある。
書かないと、監査の記述が発言として引用される。

### 照合が拾えない穴を文脈で埋める

**全エンジンが同じ間違え方をした箇所は、照合では検出できない。**
実データでは「期初」が全4エンジンで「気象」になり、
「大体気象の目標を3月から4月ぐらいに立てまして」がそのまま出ていた。
音響からの多数決では原理的に届かない。残っている手掛かりは文脈だけになる。

そこで `PlausibilityChecker`（`Sources/UtsushiCore/Audit/`）が、
言語モデルに「日本語として意味が通らない語」を指摘させる。
**ただしモデルに本文を書かせないという原則は変えていない。**

```
`[00:00:04]` 大体気象の目標を3月から4月ぐらいに立てまして、…
> ⚠︎ 文脈に合わない語: 「気象」→「期初」かもしれない
```

モデルが返せるのは**行番号・その行にある語・ありうる語**の3つだけで、
本文を返すフィールドが型に存在しない。返ってきた指摘は `PlausibilityGate` を通る:

| 条件 | 落とす理由 |
|---|---|
| **その語が本文に実在すること** | 許すと、存在しない語についての注意書きが本文の横に並ぶ |
| 行番号が実在すること | 捏造した行への指摘を防ぐ |
| 1〜8文字、長さ比2倍以内 | 文まるごとの書き換え提案を拒む |
| 漢字・カタカナ・英数字を含むこと | 助詞のゆれを指摘されても読み手にできることが無い |
| 元に無い英字を持ち込まないこと | 文脈の指摘ではなく創作 |
| 同じ指摘が2回出ること | 1回だけの指摘はモデルの気まぐれ |

`EditGate`（校正）ほど厳しくしていないのは、**ここでは本文を書き換えないから**。
書き換えるなら読み一致まで要るが、それだと「気象（きしょう）→期初（きしょ）」は落ちてしまう。
横に候補を並べるだけなら、誤指摘の代償は読み手が一瞬迷うことで済む。

**未検証。** ゲートと司令塔の単体テストは通っているが、
**実モデルが実際に「気象」を拾えるかは確認できていない。**
この機能を書いた時点で別プロセスが13GBを保持しており、
`availability` は `.available` を返すのに実際の呼び出しが弾かれ続けた:

```
FoundationModels.LanguageModelError Code=-1
  com.apple.SensitiveContentAnalysisML error 15
  → Not executed due to current system state ["CriticalMemoryPressure"]
```

事前チェックでは分からない失敗なので、**「モデルが動かなかった」と「動いて外した」を
テスト側で分けてある**（前者は skip、後者は失敗）。両方とも結果は0件で同じ形になり、
区別しないと環境の問題を製品の問題として読んでしまう。実際に一度読み違えた。

確認は次のコマンドで行う（モデルが使えなければ skip される）:

```bash
xcodebuild -project Utsushi.xcodeproj -scheme Utsushi \
  -destination 'platform=macOS,arch=arm64' \
  -only-testing:UtsushiTests/PlausibilityRealModelTests test
```

## 要約

`Sources/UtsushiCore/Summary/`。モデルに返させるのは
**行番号・30文字以内の見出し・種別**の3つだけで、本文を返すフィールドが型に存在しない。
要約の本文は文字起こしのセグメントからそのまま引用される。

見出しだけはモデルが書くので、`SummaryGate` が別の条件で検証する
（要約は言い換えなので、校正で使っている読み一致は使えない）:

- 引用に無い**数値**を含む見出しは棄却。半角・全角・漢数字は同じ値に正規化して比較するので、
  「二十名」を「20名」と書き直した見出しは通る
- 引用に無い**英数字トークン**を含む見出しは棄却
- 引用に無い**カタカナ語**（3文字以上）を含む見出しは棄却
- 40文字超・2文字未満は棄却

棄却された場合、要点そのものは残したまま、見出しだけを原文の先頭から機械的に切り出す。
UI と出力にはどちらの見出しかが明示される。
存在しない行番号を指してきた要点は丸ごと捨てる（引用の無い要点＝モデルの作文になるため）。

長い収録は Foundation Models の文脈長（8,192トークン ≒ 日本語1万文字）に収まる単位に割る。
既定は1塊3,000文字。

## 設定の保存

エンジン・モデル・照合対象・各閾値は
`~/Library/Application Support/Utsushi/settings.json` に保存され、次回起動時に復元される。
保存後にモデルカタログが変わっていた場合、実在しない ID は読み込み時に落とされる
（選んだつもりで何も起きない状態を作らないため）。

設定からパイプライン設定への変換は `SessionSettings.makeConfiguration` の1か所だけを通る。
UI 側に設定をばらして持っていたときに「画面には出ているが渡し忘れる」不具合を実際に出したので、
渡し忘れが構造的に起きないようにしてある。

## 必要環境

- macOS 26 以降（Foundation Models / SpeechAnalyzer のため）
- Apple Silicon
- 校正機能には Apple Intelligence が有効であること（無効でも文字起こしと検証層は全機能動く）

## セットアップ

```bash
brew install cmake xcodegen
script/bootstrap.sh          # whisper.cpp を取得・ビルドし Xcode プロジェクトを生成
vendor/build_sherpa.sh       # 照合用エンジン（sherpa-onnx v1.13.4 静的）をビルド
script/build_and_run.sh verify
script/build_and_run.sh test
```

2時間超の手元素材で本番サイズ検証まで行う場合（素材自体はリポジトリへ入れない）:

```bash
UTSUSHI_PRODUCTION_MEDIA=/absolute/path/to/recording.mov xcodegen generate
DEVELOPER_DIR=/Applications/Xcode-beta.app/Contents/Developer \
  xcodebuild -project Utsushi.xcodeproj -scheme Utsushi \
  -destination 'platform=macOS,arch=arm64' test \
  -only-testing:UtsushiTests/RealAudioIntegrationTests/testProductionLengthRecordingHasNoTextInsideSilence
```

Xcode のテストランナーは呼び出し元シェルの環境変数を直接継承しないため、1行目で
XcodeGen がテスト scheme に素材パスを渡す。未指定で生成した場合、この長尺試験だけは
理由を表示して skip し、通常のテストには影響しない。

`script/build_and_run.sh` のサブコマンド:

| | |
|---|---|
| `build` / `run` | Debug ビルド、起動 |
| `verify` | ビルドして起動し、実際にプロセスが生きているかまで確かめる |
| `test` | 全テスト（実音声・実モデルを使うものを含む。初回はモデルのダウンロードが入る） |
| `release` | Release ビルド |
| `install` | Release ビルドして `/Applications` に入れる |
| `dist` | 配布用 `.zip` を作る |
| `icon` | アイコンを描き直す（`script/make_icon.py`） |
| `logs` | 起動して `log stream` を張る |
| `clean` | `build/` と生成した xcodeproj を消す |

`vendor/build_sherpa.sh` がタグを固定しているのは再現性のためだが、実害もある:
master は onnxruntime 1.27.1 を pin しているのに上流がそのリリースアセットを差し替えており、
ハッシュ不一致で configure が落ちる。v1.13.4（1.27.0 を pin）なら通る。

音声認識モデル（large-v3-turbo 1.6GB / 照合用 160MB〜1.0GB）は `.app` に同梱せず、
初回実行時に `~/Library/Application Support/Utsushi/Models` へダウンロードする。
どのモデルがまだ手元に無く、合計いくつ落ちるかは、開始を押す前に画面に出る。
サイズが期待値と一致しないファイルは破棄され、途中で切れたダウンロードを使うことはない。
`Models/<モデルID>/<ファイル名>` に置くが、以前の平置きレイアウトも読めるようにしてあるので、
更新しても 1.6GB を再取得することはない。

## 配布について

`project.yml` は Hardened Runtime を有効にし、entitlements（サンドボックス・
ユーザー選択ファイル読み書き・ネットワーク）を最初から設定してある。署名は ad-hoc（`-`）。
Developer ID で配布する場合は `CODE_SIGN_IDENTITY` と `DEVELOPMENT_TEAM` を差し替え、
公証に回すだけでよい。whisper.cpp は静的リンクなので、署名対象の dylib は増えず
`disable-library-validation` も不要。

`script/build_and_run.sh dist` で `.zip` を作れるが、**ad-hoc 署名のままなので
他の Mac では Gatekeeper に止められる**。受け取る側は初回だけ Finder で
右クリック →「開く」が要る。ここを消すには Apple Developer Program（有償）の
Developer ID 証明書と公証が必要で、このリポジトリでは対応していない。
自分の Mac で `install` して使う分にはこの問題は起きない。
